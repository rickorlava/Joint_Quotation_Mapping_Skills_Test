# 结构性掉期产品的目标识别

## 0. 文档定位
本文件定义结构性掉期报价 agent 的 **用户目标识别方式**

### 互斥原则

K 和 term 不能同时指定。如果用户明确地同时给出了 K 和 term，agent **必须拦截**，通过 `chat` 让用户二选一，不得调脚本。

**判定标准**：这里的同时给出指的是**明确地**同时给出 K 和 term。如果参数是根据**市场观点**隐含的，则不算"同时给出"。具体分三种情形：

1. **两个参数都明确给出** → 拦截。例如 "3m结构性掉期购汇报价，我想做到7.2" 同时指定了 3m 的 term 和 7.2 的 K
2. **一个明确 + 一个市场观点隐含** → 以明确参数为准，按对应直接表达处理。例如 "3m购汇...我觉得人民币不会破7" 中 term 明确、7 是市场观点，不以"同时给出"论
3. **两个都来自市场观点隐含** → 拦截。例如 "我觉得未来6个月人民币不会破7" 中 6m 和 7 都是隐含参数，作为输入非法，触发拦截

同时给出的情形（情形1和3），使用以下 `chat` 模板进行追问：

```
<<<TYPE_START>>> chat <<<TYPE_END>>>
<<<CONTENT_START>>>
结构性掉期要求执行价与期限对应唯一,无法同时满足您给出的 K={K} 与 {term}。
请问您希望以哪一侧作为约束?
- 以 K={K} 求对应期限
- 以 {term} 求对应 K
<<<CONTENT_END>>>
```

若客户同时给了市场观点和明确的结构性掉期参数（情形2），处理方式参考 **2.3 混合表达**章节。

## 1. 结构性掉期对客户的补贴价值

结构性掉期的期权费补贴到**掉期的近端**,使得：
- 掉期近端实际成交价比标准掉期更优
- 代价是承担期权被行权的风险

用户除了对 K 和 term 参数直接表达，也可以对补贴点数来表达需求

## 2. 用户的表达方式

用户对结构性掉期的表达可以分为专业的直接需求表达和非专业的间接表达。

### 2.1 直接表达
**直接表达**的特点为直接给出符合结构性掉期报价范式的输入模式，也就是 对 K 和 term 的直接需求。

### 2.1.1 对 term 的直接要求
**输入条件**: `term` 或 `delivery_date` 明确，且 K / target_prem_pips 都未给出
- 例子：`term` 明确见示例A1，`delivery_date` 明确见示例 A4
- 映射：识别到此目的后，将报价范式映射到 `1.1 基准单点报价给 term 求 K`

### 2.1.2 对 K 的直接要求
**输入条件**: `desired_strike` 明确，且 term / delivery_date / target_prem_pips 都未给出
- 例子：见示例A2
- 映射：识别到此目的后，将报价范式映射到 `1.2 基准单点报价给 K 求 term`

### 2.1.3 对 term 和 K 都有要求
**输入条件**: 同时给出了 `desired_strike` 和 `term` / `delivery_date`
- 例子：见示例E1
- 映射：识别到此目的后，参照 §0 互斥原则执行过约束拦截

### 历史格式兼容的标准表达

老系统存在六字段位置格式:

```
产品 币种 期限 中收 方向 产品报价
```

**历史六字段格式** 仅作兼容识别,不作为推荐形态
- 例子：见示例A3
- 映射：识别到此目的后，将报价范式映射到 `1.1 基准单点报价给 term 求 K`

### 2.1.4 方向对比
**输入条件**: 用户同时要求结汇和购汇对比，如 "结汇和购汇都报一下"
- 映射：识别到此目的后，将报价范式映射到 `1.6 方向对比`

### 2.1.5 币种对比
**输入条件**: 用户要求多个币种对比，如 "USDCNY 和 EURCNY 都报一下"
- 映射：识别到此目的后，将报价范式映射到 `1.7 币种对比`

### 2.2 间接表达
**间接表达**的特点是非专业客户的语句中没有直接给出对 K 的要求，而是通过**市场观点**来隐含一个对 K 的位置。

Agent 必须从客户的观点中反推出合理的 K 以及隐含的结汇与购汇方向。由于**市场观点**不是标准的表达，下面会给出几种常见的市场观点表达类型，以及对应的识别方式。

映射：
- 对于隐藏观点为 K 的，确定 K 和方向后，应当走**1.2 基准单点报价给 K 求 term**
- 对于**补贴点数表达**和**结果导向表达**，在识别出用户所需要的补贴点数后，走报价范式 **1.5 按近端补贴点数反查**

#### 2.2.1 否定式观点
**否定式观点** 即用户认为汇率不太可能到达某点位，例如
- "我觉得人民币不会贬值到 7.20"
- "汇率不太可能跌破 6.80"
- "应该不会破 7.30"

**K的推理路径**：用户认为不太可能到达的点位，正是适合作为 K 的位置，因为客户认为不会发生的事件如果确实没有发生，卖出的期权就不会被行权，客户可以获取近端的补贴的期权费，因此客户愿意承担对应的被行权风险。

**方向的推理路径**：客户的方向由表达本身决定：
- "不会贬值到 X" → `direction = settle`(结汇情境)
- "不会升值到 X" → `direction = purchase`(购汇情境)
- "不会跌破""不会破 X" → 需结合上下文判断方向,不确定时通过 `chat` 追问

**映射**：推导出 K 和方向后，将报价范式映射到 `1.2 基准单点报价给 K 求 term`

#### 2.2.2 区间肯定式观点

**区间肯定式观点** 即用户认为汇率大概率会落在某个区间，例如

- "我觉得汇率大概率在 7.00 到 7.10 之间"
- "应该会在 6.95~7.05 这个范围"
- "未来这段时间应该都在 7.0 附近"

**K的推理路径**：用户认为的汇率区间为"高概率发生区"，但 K 只有一个，因此 K 应当设在用户认为不太可能发生的区间外侧，使得未来汇率的确落在用户所认为的区间时，客户得以获得近端的补贴的期权费，且期权不会被行权。具体落在区间哪边需要由方向决定。
- 结汇方向: K 设在区间**上沿之上**，因为只要汇率不涨破区间之上,期权就不会被行权，符合客户对汇率的**区间观点**。例:区间 7.00-7.10,结汇 → K 取 7.10 或略高于此
- 购汇方向:K 设在区间**下沿之下**。因为只要汇率不跌破区间之下，期权就不会被行权，符合客户对汇率的**区间观点**。例:区间 7.00-7.10,购汇 → K 取 7.00 或略低于此

**方向的推理路径**：由于区间观点并未对方向做出判断，因此需要结合其他的客户上下文进行方向判断，如果客户没有确定方向，则需要通过 `chat` 追问方向

**映射**：推导出 K 和方向后，将报价范式映射到 `1.2 基准单点报价给 K 求 term`

#### 2.2.3 安全边际表达
**安全边际** 表达并非 **市场观点**，而是对 K 给出了 **相对位置** 而非明确的绝对位置。例如：
- "K 离当前现货远一点"
- "我想 K 设保守一点,远离市场价"
- "K 别太冒险"

**K的推理路径**：这类表达没有给出数值和市场观点，无法根据表达得到 K, 因此要通过 `chat` 引导用户给出自己的观点，询问客户是否希望：
- 给出一个具体的 K 值或区间观点
- 如果用户没有给出 K 值或区间观点的意愿，则根据客户的安全边际表达，按照当前市场标准的"保守" / "中性" / "激进"位置自动选取，选取之前要引导客户给出方向的偏好

**方向的推理路径**：这类表达没有给出方向的观点，因此要通过 `chat` 引导客户给出方向性偏好

**映射**：识别到此目的后，将报价范式映射到 `1.2 基准单点报价给 K 求 term`

#### 2.2.4 补贴点数表达

**补贴点数表达** 为用户没有指定 K 和 term，而是对期权费补贴的点数

**K的推理路径**：K 需要按照 `quotation_format.md` 的 1.5 按近端补贴点数反查方式得到

**方向的推理路径**：
1. 先确定用户是否有方向性偏好
2. 若无法确定，则使用 `chat` 追问用户的方向偏好
3. 若客户要求每个方向都扫描，则使用 `chat` 与用户协商扫描期限，不超过3个

**映射**：识别到此目的后，将报价范式映射到 `1.5 按近端补贴点数反查`

### 2.3 混合表达
**混合表达** 即客户既给出了直接参数，又给出了市场观点，比如

> "应该在 7.0 附近,不会破 7.15,我做个 3M 结汇的"

**K的推理路径**：这种表达为混合式，规定一个优先级：**直接参数 > 否定式观点 > 区间观点 > 安全边际**

报价范式映射：
- 直接参数的优先级最高。
    - 如果直接参数为 term/delivery，走**1.1 基准单点报价给 term 求 K**或者**1.1.1 基准单点报价给 delivery 求 K**
    - 如果直接参数为 K，走**1.2 基准单点报价给 K 求 term**
- 如果没有直接参数，所有的参数要从**市场观点**种隐含，则市场观点有 term/delivery 走**1.1 基准单点报价给 term 求 K**或者**1.1.1 基准单点报价给 delivery 求 K**，如果市场观点有 K 走**1.2 基准单点报价给 K 求 term**，如果市场观点既隐含了 K 又隐含了 term/delivery，则需要追问
- 方向的推理，如果客户有明确直接参数，以直接参数为准，如果没有，则按照观点优先级，参考各个**市场观点**对方向的推理或追问方式。


混合表达的详细例子见 example B1

### 2.4 结果导向表达

**结果导向表达** 为用户没有直接提补贴点数，但给出了所希望达成的经过补贴后近端的价格

**K的推理路径**：这种表达必须要结合当前远期的价格，使用远期价格减和补贴后价格差得到补贴费用，再走补贴点数表达的推理路径

**方向的推理路径**：方向性隐含在了补贴后掉期近端价格与远期价格相对高低中，若补贴后近端价格高于远期价格，则客户是想 sell 掉期，那么方向应该为结汇, 反之购汇

**映射**：推导出补贴点数后，走补贴点数表达的推理路径，将报价范式映射到 `1.5 按近端补贴点数反查`

### 2.5 信息不足情形
**输入条件**: K、term、delivery_date、target_prem_pips **全部**缺失
**处理**: 通过 `chat` 追问，不得擅自选择默认值报价——三种入口在业务上不对称。

## 3. 组合模式行为约束

### 3.1 组合模式前提条件
组合模式适用于当用户需求**无法由一次调用完成**，但可以被拆分为若干**语义独立、目标清晰**的子调用时。进入组合模式要求同时满足以下3条：
1. 用户需求确实需要多维度比较或分步完成
2. 每一次调用都能回答"这一次要解决什么子问题"
3. 子调用之间互相独立或有清晰依赖链

### 3.2 先规划后执行
进入组合前必须形成调用计划清单，按计划执行，不在过程中无规划新增调用。

调用计划清单格式：
```
调用 1:<目标> → 参数:<...>
调用 2:<目标> → 参数:<...>
...
汇总方式:<表格 / 筛选后返回>
```

规划与试错的划分：
| 组合求解 | 试错行为 |
|---|---|
| 每次调用的子目标不同 | 目标相同或相似 |
| 产生独立新信息 | 产生冗余信息 |
| 事前有规划 | 事后看结果再决定 |
| 调用数可预期 | 调用数不受控 |

### 3.3 预算交互规则
- 调用次数的预算超出时，通过 `chat` 与用户协商拆分
- 不允许执行中途临时扩展预算
