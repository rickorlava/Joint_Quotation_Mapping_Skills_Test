# 结构性掉期产品的输出范式

## 0. 文档定位
本文件定义结构性掉期报价 agent 最终输出中 **可接受的几种固定形式**

## 1. 给出了 K or term 的单次求解模式

### 1.1 给 K 求 term
**输入**:`desired_strike` 明确,且 term / delivery_date / target_prem_pips 都未给出
**处理**:单次调用脚本,返回对应 term 及掉期细节。

### 1.2 给 term 求 K
**输入**:`term` 或 `delivery_date` 明确,且 K / target_prem_pips 都未给出
**处理**:单次调用脚本,返回对应 K 及掉期细节。

## 2. 输出追问
### 2.1 用户同时给出了 term 和 K
**输入**:同时给出 `desired_strike` 和 `term` / `delivery_date`
**处理**:**agent 必须拦截**,通过 `chat` 追问，让用户二选一。不得调脚本，典型追问文案：
```
<<<TYPE_START>>> chat <<<TYPE_END>>>
<<<CONTENT_START>>>
结构性掉期要求执行价与期限对应唯一,无法同时满足您给出的 K={K} 与 {term}。
请问您希望以哪一侧作为约束?
- 以 K={K} 求对应期限
- 以 {term} 求对应 K
<<<CONTENT_END>>>
```
### 2.2 信息不足的情形
**输入**:K、term、delivery_date、target_prem_pips **全部**缺失
**处理**:通过 `chat` 追问,**不要**擅自选择默认值报价——三种入口在业务上不对称。

## 3. 组合模式

该输出范式适用于当用户需求**无法由一次调用完成**,但可以被拆分为若干**语义独立、目标清晰**的子调用时,进入组合模式。进入该模式要求同时满足以下3条：
1. 用户需求确实需要多维度比较或分步完成
2. 每一次调用都能回答"这一次要解决什么子问题"
3. 子调用之间互相独立或有清晰依赖链


### 3.1 沿曲线扫描 term 区间
**沿曲线扫描 term**(扫一段 term 区间)
**触发**:用户给出 term 区间,如"1M 到 6M 都给我看看"
**处理**:
- 在区间内选择若干代表性 term 点位(建议 3~5 个,均匀分布)
- 每个 term 调一次脚本(每次调用只带 `--term`)
- 汇总为表格,每行标注对应的子调用维度(K / term / 方向 / 币种 / 补贴点数)

### 3.2 沿曲线扫描 K 区间
- **沿曲线扫描 K**(扫一段 K 区间)
**触发**:用户给出 K 区间,如"K 从 7.00 到 7.20 扫一下"
**处理**:
- 在区间内选择若干代表性 K 点位
- 每个 K 调一次脚本(每次调用只带 `--desired-strike`)
- 汇总为表格,每行标注对应的子调用维度(K / term / 方向 / 币种 / 补贴点数)

### 3.2 按补贴点数反查
- **按补贴点数反查** 模式为用户没有给出 K or term, 而是 **当用户表达 `target_prem_pips` 时触发**。

#### 3.2.1 标准流程

0. **方向确认**：确定用户是否有方向性偏好
- 若无法确定，则使用 `chat` 追问用户的方向偏好
- 若客户要求每个方向都扫描，则使用 `chat` 与用户协商扫描期限，不超过3个


1. **扫描阶段**:在 1M~12M 期限范围内,选取一组代表性 term(如 1M、2M、3M、4M、6M、9M、12M 等),每个 term 调一次脚本,取回对应的补贴点数
2. **筛选阶段**:对扫描得到的 (term, 补贴) 数据点,找出补贴数值**最接近用户目标的两个 term 点位**(一个略高、一个略低,方便用户对比)
3. **输出阶段**:只把筛选出的两个方案返回给用户,表格列明 term、K、补贴点数,并标注"这是最接近您目标 {target_prem_pips} 点的两个方案"

#### 3.2.3 当目标补贴点数超出曲线可达范围

若扫描后发现目标补贴点数**明显高于或低于**曲线所有点的取值:
- 仍然返回补贴最接近目标的那个 term 点位
- 在输出中明确说明:"您目标的补贴点数在当前市场曲线上不可达,以下是最接近的方案"


### 3.3 预算控制

### 3.3.1 要求

- 扫描数量必须 ≤ 6 次预算
- 推荐的**期限扫描**集合(示例):`1M、2M、3M、6M、9M、12M` 共 6 个
    - agent 可根据用户语言微调——如果用户说"半年以内",则聚焦在 1M~6M
- 调用次数的预算超出时通过 `chat` 与用户协商拆分
- 不允许执行中途临时扩展预算

### 3.3.2 预算实施方法
**先规划后执行**。规划与试错的划分：
| 组合求解 ✅ | 试错行为 ❌ |
|---|---|
| 每次调用的子目标不同 | 目标相同或相似 |
| 产生独立新信息 | 产生冗余信息 |
| 事前有规划 | 事后看结果再决定 |
| 调用数可预期 | 调用数不受控 |

进入组合前必须形成调用计划清单:

```
调用 1:<目标> → 参数:<...>
调用 2:<目标> → 参数:<...>
...
汇总方式:<表格 / 筛选后返回>
```

按计划执行,不在过程中无规划新增调用。

### 3.4 输出汇总
- 汇总为表格,每行标注对应的子调用维度(K / term / 方向 / 币种 / 补贴点数)

- 只输出筛选后的两个方案,不输出扫描过程中的全部中间数据——**中间数据是 agent 的内部工作,不是用户的答案**。

## 4. 方向对比
**触发**:用户说"结汇和购汇都报一下"
**处理**:两次调用,方向分别为 settle 和 purchase。两行一表。

## 5. 币种对比
**触发**:用户说"USDCNY 和 EURCNY 都报一下"
**处理**:两次调用,币种各一次。两行一表。
