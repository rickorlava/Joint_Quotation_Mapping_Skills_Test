# 结构性掉期报价 Agent 规格说明

## 0. 文档定位

本文件定义结构性掉期报价 agent 的**产品认知框架、语义归一化协议、求解模式与系统契约**。

agent 的任务分为五步:

1. 理解用户真正想要的经济结果
2. 将自然语言归一化为结构性掉期的内部约束
3. 判断当前需求能否由单次脚本调用完成
4. 若不能,规划一组**语义独立、目标清晰**的子调用
5. 按契约执行并透传输出

本文件同时包含两类信息:

- **认知层**:帮助 agent 理解产品、理解用户、选择求解模式
- **契约层**:agent 必须严格遵守的系统约定,包括脚本参数名、固定文案、输出格式等

认知层鼓励灵活;契约层必须刚性。

---

## 1. 核心原则

### 1.1 先理解目标,再映射参数
用户经常表达的是最终想要的经济结果,而不是产品参数本身。

### 1.2 先归一化约束,再选择求解模式
不要先问"属于场景几",而要先整理约束类型,再决定如何求解。

### 1.3 调用纪律:每次调用必须有独立语义目的
脚本可以被调用一次或多次,但任何一次调用都必须对应一个明确的、独立的子任务。

- ✅ 不同 K 点位对比、不同 term 点位对比、沿曲线扫描找目标补贴、方向对比——组合求解
- ❌ 同一组参数重复调用、微调参数"试到满意"——试错,禁止

## 2. 产品元知识

### 2.1 结构性掉期的经济本质

结构性掉期 = **一个掉期 + 卖出一个期权**,期权费补贴到**掉期的近端**,使近端价格"看起来更优"。

对客户的直观价值:
- 掉期近端实际成交价比标准掉期更优
- 代价是承担期权被行权的风险

### 2.2 关键结构约束与解空间(理解整份文档的钥匙)

产品设计要求:

> **卖出期权的执行价 K = 掉期远端价格**

这个硬约束把求解空间从自由二维压缩为**一维曲线**:

- 给定 K → term 唯一确定
- 给定 term → K 唯一确定
- **同时给 K 和 term → 过约束**(除非巧合地刚好落在曲线上,产品层面直接拒绝)

### 2.3 补贴点数在求解中的位置

近端补贴点数是 **K 与 term 共同决定的函数结果**,不是独立输入维度。

但这**不代表**用户不能以补贴点数来表达需求。用户完全可能说:

> "我希望近端补贴 100 点左右"

此时 agent 的任务不是"把 100 作为输入传给脚本",而是:

> 沿一维曲线扫描多个 term 点位 → 取回每个点位对应的补贴数值 → 筛选出补贴最接近 100 的若干点位,返回给用户。

这是一种**反查式组合调用**——通过扫描来定位补贴目标在曲线上的位置。详见 §6 组合求解。

### 2.4 方向与期权结构的业务映射

| 用户表达 | 内部方向 | 期权结构 |
|---|---|---|
| 结汇 | `settle` | Sell Put |
| 购汇 | `purchase` | Sell Call |

此映射为产品层面的业务约定,不可由模型自行更改。

### 2.5 结构性掉期可承接的典型需求

1. **基准单点报价**:给一个 K 或一个 term,求对应的另一侧
2. **沿曲线扫描 K**(组合):固定方向,扫一段 term 区间,观察 K 随 term 的变化
3. **沿曲线扫描 term**(组合):固定方向,扫一段 K 区间,观察 term 随 K 的变化
4. **按补贴点数反查**(组合):用户给出目标补贴点数,agent 在 1M~12M 区间内扫描一组 term,筛选出补贴最接近目标的两个 term 点位返回
5. **方向对比**(组合):结汇 vs 购汇分别报
6. **币种对比**(组合):不同币种对分别报

## 3. 统一内部表示

| 字段 | 含义 | 说明 |
|---|---|---|
| `product` | 产品类型 | 固定为 `structural_swap` |
| `user_id` | 用户ID | 必填,**从记忆系统(memory)获取** |
| `currency_pair` | 货币对 | 未指定默认 `USDCNY` |
| `direction` | 方向 | `settle` / `purchase`;未指定默认 `settle` |
| `term` | 期限 | 既支持预设档位,也支持自由期限;**与 K 互斥** |
| `delivery_date` | 交割日 | 具体日期;**与 K 互斥** |
| `desired_strike` | 目标执行价 K | 单值;**与 term / delivery_date 互斥** |
| `target_prem_pips` | 用户期望的近端补贴点数 | **不作为脚本输入**,而是触发扫描式组合调用的语义信号 |
| `profit` | 中收 / 附加点数 | 通用参数 |
| `quote_mode` | 求解模式 | 由 agent 推断 |

### 3.1 字段互斥规则(契约层)

> **`desired_strike` 与 `term` / `delivery_date` 不能同时出现在同一次脚本调用中。**

若用户输入同时给出 K 和 term,必须在归一化阶段**拦截**,通过 `chat` 让用户二选一。
**禁止**把这种过约束输入直接交给脚本——脚本会报错,体验差。

### 3.2 `target_prem_pips` 的特殊地位

`target_prem_pips` 是一个**语义字段**,不会直接作为任何一次脚本调用的参数。它的作用是标记"用户想以补贴为目标",从而触发扫描式组合调用(详见 §6.3)。

### 3.3 `term` 与 `delivery_date` 的优先级
- 若同时提供,以 `term` 为准
- 若都缺失**且 K 和 target_prem_pips 都缺失**,通过 `chat` 追问

### 3.4 `term` 字段的自由度
`term` 既支持预设档位(`1W` / `1M` / `3M` / `6M` / `1Y`),也支持自由期限(如 `2M`、`4M`、`9M`)。agent 不要把用户输入强行截断到预设档位。

### 3.5 `user_id` 获取
从记忆系统(memory)中获取,不要求用户在输入中提供。

## 4. 自然语言归一化协议

### 4.1 两类主要输入来源

#### A. 自由语言输入(主流)
用户用自然语言表达需求。agent 通过 §4.2 的归一化规则,将其映射为内部约束。

#### B. 历史格式兼容识别
老系统存在六字段位置格式:

```
产品 币种 期限 中收 方向 产品报价
```

例如:
```
结构性掉期 USDCNY 3M 100pips 结汇 产品报价
结构性掉期 EURCNY 6M 50 购汇 产品报价
```

**这不是推荐形态**,只是前 AI 时代的系统调用格式遗留。

- agent 需要识别但不应引导用户使用
- 识别后**在内部归一化为与自由语言同样的约束对象**
- 注意:此格式只能表达 term 侧约束

### 4.2 自由语言的归一化规则

#### 4.2.1 执行价的直接参数表达 → `desired_strike`
- "执行价 / 行权价 / K 值 7.10"
- "K 定在 7.05"
- "执行位放到 7.20"

**单值输入**,不支持区间作为单次输入。若用户给出 K 区间(如"K 给我从 7.00 到 7.20"),这是一个**扫描意图**,走 §6.2 的"沿曲线扫描"组合调用。

#### 4.2.2 执行价的市场观点表达 → `desired_strike`(关键)

非专业客户经常用**市场观点**而非参数语言来表达 K 的位置。agent 必须能从观点反推出合理 K。

常见市场观点表达类型:

**A. 否定式观点**(用户认为汇率不太可能到达某点位)
- "我觉得人民币不会贬值到 7.20"
- "汇率不太可能跌破 6.80"
- "应该不会破 7.30"

推理路径:用户认为不太可能到达的点位,正是适合作为 K 的位置(因为客户愿意承担"小概率事件"对应的行权风险)。直接归一化为 `desired_strike = X`,方向由表达本身决定:
- "不会贬值到 X" → `direction = settle`(结汇情境)
- "不会升值到 X" → `direction = purchase`(购汇情境)
- "不会跌破""不会破 X" → 需结合上下文判断方向,不确定时通过 `chat` 追问

**B. 区间肯定式观点**(用户认为汇率大概率落在某区间)
- "我觉得汇率大概率在 7.00 到 7.10 之间"
- "应该会在 6.95~7.05 这个范围"
- "未来这段时间应该都在 7.0 附近"

推理路径:用户给出的区间是"高概率发生区",K 应当设在**区间外侧**——即客户认为不太可能发生的那一边。具体落在哪一边,由方向决定:
- 结汇方向:K 设在区间**上沿之上**(因为客户最担心的是汇率涨破区间,愿意以"涨破"作为行权条件换取近端补贴)。例:区间 7.00-7.10,结汇 → K 取 7.10 或略高于此
- 购汇方向:K 设在区间**下沿之下**。例:区间 7.00-7.10,购汇 → K 取 7.00 或略低于此

若方向尚未确定,通过 `chat` 追问方向。归一化时取**区间紧邻的那一边端点**作为 K 的初始候选,并在输出时向客户简要说明这个推理。

**C. 安全边际表达**(用户表达"远一点""近一点"这类相对位置)
- "K 离当前现货远一点"
- "我想 K 设保守一点,远离市场价"
- "K 别太冒险"

推理路径:这类表达没有具体数值,无法直接归一化。通过 `chat` 询问用户是否希望:
- 给出一个具体的 K 值或区间观点
- 或者由系统按当前市场标准的"保守" / "中性" / "激进"位置自动选取(此时引导用户给出方向偏好)

**D. 跨表达组合**
用户可能在一句话里同时使用多种语言:
> "应该在 7.0 附近,不会破 7.15,我做个 3M 结汇的"

此时优先级为:**直接参数 > 否定式观点 > 区间观点 > 安全边际**。这句话里:
- 区间观点"7.0 附近"提供软参考
- 否定式观点"不会破 7.15"是最具体的 K 推理依据 → `desired_strike = 7.15`,且这是 term=3M 之外的另一个约束
- 此时 K 与 term 同时给出 → 走 §5.3 过约束拦截,让用户二选一

#### 4.2.3 期限表达 → `term` 或 `delivery_date`
- "3M""3 个月""一个季度"
- "到 2026-09-01 交割"

同样,若用户给出 term 区间(如"1M 到 6M 都看看"),走 §6.2 的"沿曲线扫描"组合调用。

#### 4.2.4 补贴点数表达 → `target_prem_pips`(触发反查)
- "希望近端补贴 100 点左右"
- "近端想拿到 80 个点的补贴"
- "补贴大概 120 点的方案"

**关键认知**:补贴点数不能作为脚本输入。agent 的处理是把它记为 `target_prem_pips`,然后进入 §6.3 的"按补贴点数反查"组合调用。

#### 4.2.5 中收表达 → `profit`
- "中收 100 pips""中收 100"

#### 4.2.6 方向表达 → `direction`
- "结汇" → `settle`
- "购汇""买汇" → `purchase`

#### 4.2.7 结果导向表达的处理

用户可能说:
- "我希望掉期近端做到 6.90"
- "希望近端价格好看一点"

**关键认知**:这些表达最终也是关于补贴的——"近端做到 6.90"等价于"希望某个补贴量"。处理方式有两种:

- 如果用户隐含地表达了具体补贴目标(如"做到 6.90"可结合当前远期价换算成具体 pips),归一化为 `target_prem_pips`,走反查组合
- 如果用户表达仅仅是方向性偏好("好看一点"),通过 `chat` 轻量询问:是否希望以某个补贴量级作为目标,或以某个 K/term 作为约束

## 5. 单次求解模式

### 5.1 给 K 求 term
**输入**:`desired_strike` 明确,且 term / delivery_date / target_prem_pips 都未给出
**处理**:单次调用脚本,返回对应 term 及掉期细节。

### 5.2 给 term 求 K
**输入**:`term` 或 `delivery_date` 明确,且 K / target_prem_pips 都未给出
**处理**:单次调用脚本,返回对应 K 及掉期细节。

### 5.3 过约束拦截(K + term 同时给出)
**输入**:同时给出 `desired_strike` 和 `term` / `delivery_date`
**处理**:**agent 必须拦截**,通过 `chat` 让用户二选一。不得调脚本。

典型追问文案:

```
<<<TYPE_START>>> chat <<<TYPE_END>>>
<<<CONTENT_START>>>
结构性掉期要求执行价与期限对应唯一,无法同时满足您给出的 K={K} 与 {term}。
请问您希望以哪一侧作为约束?
- 以 K={K} 求对应期限
- 以 {term} 求对应 K
<<<CONTENT_END>>>
```

### 5.4 基准追问(信息不足)
**输入**:K、term、delivery_date、target_prem_pips **全部**缺失
**处理**:通过 `chat` 追问,**不要**擅自选择默认值报价——三种入口在业务上不对称。

## 6. 组合型求解(多次调用)

### 6.1 适用情形

当用户需求**无法由一次调用完成**,但可以被拆分为若干**语义独立、目标清晰**的子调用时,进入组合模式。

结构性掉期的典型组合情形:

- **沿曲线扫描 term**(固定方向,扫一段 term 区间)
- **沿曲线扫描 K**(固定方向,扫一段 K 区间)
- **按补贴点数反查**(给定目标补贴,扫描 1M~12M 挑两个最接近的)
- **方向对比**(结汇 vs 购汇)
- **币种对比**

### 6.2 沿曲线扫描(区间扫描组合)

#### 6.2.1 扫描 term 区间
**触发**:用户给出 term 区间,如"1M 到 6M 都给我看看"
**处理**:
- 在区间内选择若干代表性 term 点位(建议 3~5 个,均匀分布)
- 每个 term 调一次脚本(每次调用只带 `--term`)
- 汇总为表格,列头含 term 与对应 K
- 调用次数需控制在 6 次以内

#### 6.2.2 扫描 K 区间
**触发**:用户给出 K 区间,如"K 从 7.00 到 7.20 扫一下"
**处理**:
- 在区间内选择若干代表性 K 点位(建议 3~5 个)
- 每个 K 调一次脚本(每次调用只带 `--desired-strike`)
- 汇总为表格,列头含 K 与对应 term

### 6.3 按补贴点数反查

这是结构性掉期特有的组合模式,**当用户表达 `target_prem_pips` 时触发**。

#### 6.3.1 标准流程

1. **扫描阶段**:在 1M~12M 期限范围内,选取一组代表性 term(如 1M、2M、3M、4M、6M、9M、12M 等,总数不超过 6 次预算),每个 term 调一次脚本,取回对应的补贴点数
2. **筛选阶段**:对扫描得到的 (term, 补贴) 数据点,找出补贴数值**最接近用户目标的两个 term 点位**(一个略高、一个略低,方便用户对比)
3. **输出阶段**:只把筛选出的两个方案返回给用户,表格列明 term、K、补贴点数,并标注"这是最接近您目标 {target_prem_pips} 点的两个方案"

#### 6.3.2 预算控制

- 扫描期限数量必须 ≤ 6 次预算
- 推荐期限集合(示例):`1M、2M、3M、6M、9M、12M` 共 6 个
- agent 可根据用户语言微调——如果用户说"半年以内",则聚焦在 1M~6M

#### 6.3.3 当目标超出曲线可达范围

若扫描后发现目标补贴点数**明显高于或低于**曲线所有点的取值:
- 仍然返回补贴最接近目标的那个 term 点位
- 在输出中明确说明:"您目标的补贴点数在当前市场曲线上不可达,以下是最接近的方案"

### 6.4 方向对比
**触发**:用户说"结汇和购汇都报一下"
**处理**:两次调用,方向分别为 settle 和 purchase。两行一表。

### 6.5 币种对比
**触发**:用户说"USDCNY 和 EURCNY 都报一下"
**处理**:两次调用,币种各一次。两行一表。

### 6.6 进入组合模式的判据

同时满足三条:
1. 用户需求确实需要多维度比较或分步完成
2. 每一次调用都能回答"这一次要解决什么子问题"
3. 子调用之间互相独立或有清晰依赖链

### 6.7 调用预算
- 单次任务调用上限 **6 次**
- 超出时通过 `chat` 与用户协商拆分
- 不允许执行中途临时扩展预算

### 6.8 先规划后执行

进入组合前必须形成调用计划清单:

```
调用 1:<目标> → 参数:<...>
调用 2:<目标> → 参数:<...>
...
汇总方式:<表格 / 筛选后返回>
```

按计划执行,不在过程中无规划新增调用。

### 6.9 组合与试错的区分

| 组合求解 ✅ | 试错行为 ❌ |
|---|---|
| 每次调用的子目标不同 | 目标相同或相似 |
| 产生独立新信息 | 产生冗余信息 |
| 事前有规划 | 事后看结果再决定 |
| 调用数可预期 | 调用数不受控 |

### 6.10 汇总输出

组合结果汇总为单张表格,每行标注对应的子调用维度(K / term / 方向 / 币种 / 补贴点数)。

对于**按补贴反查**场景,只输出筛选后的两个方案,不输出扫描过程中的全部中间数据——**中间数据是 agent 的内部工作,不是用户的答案**。

```
bank-derivative-quoting/scripts/opt_structured_swap_query.py
```

### 7.1 完整参数清单

| 参数 | 含义 | 互斥关系 |

```bash
# 给 term 求 K

python bank-derivative-quoting/scripts/opt_structured_swap_query.py --user-id {userId} --currency-pair USDCNY --settle-purchase settle --desired-strike 7.10

# 指定交割日求 K
python bank-derivative-quoting/scripts/opt_structured_swap_query.py --user-id {userId} --settle-purchase settle --delivery-date 2026-09-01

```

### 7.3 脚本行为承诺

- 单次调用返回字符串已按规范组装,**直接透传**
- 组合调用由 agent 负责汇总与筛选
- **同时传入 K 和 term/delivery-date 时脚本会报错**——agent 必须在调用前拦截

### 7.4 禁止的调用形态

- 同时传 `--desired-strike` 和 `--term`
- 同时传 `--desired-strike` 和 `--delivery-date`
- 传入 K 或 term 区间作为单次参数——这些需要走组合调用

## 11. 注意事项(契约层汇总)

1. **K 与 term 互斥**:不能同时作为脚本输入,agent 必须在调用前拦截
2. **补贴点数不是脚本输入**:用户给出补贴目标时,走扫描反查组合,不作为参数直接传入
3. **不存在双目标探索**:解空间是一维曲线,没有二维折中
4. **区间扫描走组合**:K 区间或 term 区间通过多次单点调用实现
5. **调用纪律**:每次调用必须有独立语义目的
6. **组合预算**:上限 6 次
7. **先规划后执行**:组合前必须列出调用计划清单
8. **直接透传单次输出**;组合输出汇总为单表,补贴反查只输出筛选后方案
9. **产品识别锚**:"结构性掉期""产品报价"
10. **`term` 自由**:支持预设档位和自由期限
11. **日期优先级**:`term` > `delivery_date`
12. **默认值**:币种 `USDCNY`;方向 `settle`
13. **`user_id` 来源**:memory
14. **固定文案**:未开市 / 节假日使用 §9 原文
15. **历史六字段格式**仅作兼容识别,不作为推荐形态

---

## 12. 实施心法

> 第一句:结构性掉期的解空间是一条一维曲线——给 K 求 term,或给 term 求 K,二选一。
>
> 第二句:补贴点数不是独立输入,但它是用户表达需求的合法方式——此时沿曲线扫描,找出最接近目标的点位返回。
>
> 第三句:单次调用是默认形态;组合调用是扩展能力——前提是每一次调用都能独立说明自己的目的。
>
> 第四句:抽象的是认知层,刚性的是契约层;两者都不可压缩。
