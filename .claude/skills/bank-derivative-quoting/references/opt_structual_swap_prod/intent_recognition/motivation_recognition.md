# 结构性掉期产品的目标识别

## 0. 文档定位
本文件定义结构性掉期报价 agent 的 **用户目标识别方式**

### 核心原则
**先理解目标,再映射参数**：用户经常表达的是最终想要的经济结果,而不是直接给产品参数本身。

### K 与 far-term 共存原则（架构变更）

结构性掉期现已支持 K 独立于掉期远端价格(FAR)输入。K 与 far-term 不再互斥。

- 用户可同时给出 K 和 far-term → 走 **1.4 K 确定求 prem** 或 **1.5 双目标探索**（如同时给 prem）
- 用户仅给出 K（无 far-term）→ far-term 是掉期结构的必要参数，须通过 `chat` 追问 far-term 或使用默认 far-term (6M)
- 用户仅给出 far-term → 走 **1.1 基准报价(K=FAR)**，与传统行为一致

此原则下，所有 K 相关的意图映射逻辑与其他产品（DCD、海鸥）一致。

## 0.5 脚本选型决策表（**必须遵守 — 选型错误将导致报价失败**）

结构性掉期存在**两个报价脚本**，意图识别完成后、调用脚本前**必须**按以下决策表选择正确脚本。

### 术语定义（**关键——混淆将导致报价错误**）

| 用户术语 | 含义 | 映射参数 | 对应脚本参数 |
|---|---|---|---|
| "期权费 X pips" / "补贴 X pips" / "补贴 X 点" | **期权费**（客户卖期权获得的近端补偿） | `premPips`（目标期权费） | `--prem-pips X`（`structured_swap_query.py`） |
| "中收 X pips" / "中收 X 点" | **中收**（行权后额外收益） | `profit` | `--profit X`（`opt_structured_swap_query.py`） |

**重要**："补贴" = 期权费（premPips），**不是**中收（profit）。两者是不同维度的参数：
- 期权费（补贴）→ 决定执行价 K 的位置 → 走 `structured_swap_query.py`
- 中收 → 在执行价确定后调整近端价格 → 走 `opt_structured_swap_query.py`

### 一条规则

> **用户是否给出了 K（执行价）/ prem（期权费/补贴/补贴点数）/ delta（激进/保守风格）中的任一**。

### 决策流程

```
① 提取用户所有约束参数
② 检查是否包含 K / prem / delta：
   │
   ├─ 是 → ③ 是否同时给出期限（far-term / far-delivery-date）？
   │       ├─ 是 → ✅ structured_swap_query.py（独立求解）
   │       └─ 否 → ④ 是什么参数？
   │               ├─ 仅 prem 无期限 → ✅ opt_structured_swap_query.py（补贴反查，需扫描 term 曲线）
   │               └─ 仅 K 无期限   → ⚠️ chat 追问 term（结构性掉期需要 term 锚定）
   │
   └─ 否 → ✅ opt_structured_swap_query.py（基准报价 K=FAR）
```

### 完整决策表

| 用户给了什么？ | 脚本 | 报价范式 | 为什么 |
|---|---|---|---|
| 仅 far-term | `opt_structured_swap_query.py` | 基准 K=FAR | 默认 K=远端价格 |
| 仅 far-delivery-date | `opt_structured_swap_query.py` | 基准 K=FAR | 默认 K=远端价格 |
| near-term + far-term | `opt_structured_swap_query.py` | 基准 K=FAR | 近远端期限对 |
| near-delivery-date + far-delivery-date | `opt_structured_swap_query.py` | 基准 K=FAR | **高频场景**：近远端日期对 |
| near-delivery-date + far-delivery-date + **K** | `structured_swap_query.py` | K 确定求 prem | 有执行价约束 |
| near-delivery-date + far-delivery-date + **prem** | `structured_swap_query.py` | prem 反求 K | 有期权费约束 |
| near-delivery-date + far-delivery-date + **delta** | `structured_swap_query.py` | 风格化报价 | 有风格约束 |
| **near-term + far-delivery-date**（混合格式） | `opt_structured_swap_query.py` | 基准 K=FAR | **T+3-2026-07-16** 等混合格式 |
| far-term + **K** | `structured_swap_query.py` | K 确定求 prem | 有执行价约束 |
| far-term + **prem** | `structured_swap_query.py` | prem 反求 K | 有期权费约束 |
| far-term + **delta** | `structured_swap_query.py` | 风格化报价 | 有风格约束 |
| far-term + **K + prem** | `structured_swap_query.py` | 双目标探索 | 有双约束 |
| far-term + **[K₁, K₂]** | `structured_swap_query.py` | K 区间扫描 | 有区间约束 |
| far-term + **[p₁, p₂]** | `structured_swap_query.py` | prem 区间扫描 | 有区间约束 |
| 仅 **prem**（无期限） | `opt_structured_swap_query.py` | 补贴反查扫描 | 需扫 term 曲线（组合调用） |
| 仅 **K**（无期限） | ⚠️ chat 追问 | — | 需要 term 锚定掉期结构 |

### 参数命名区别（两脚本不通用）

| 参数 | opt 脚本 | 标准脚本 |
|------|---------|---------|
| 执行价 | `--target-strike`（单值） | `--target-strikes`（1-2值） |
| 远端期限 | `--far-term` | `--far-term` |
| 近端期限 | `--near-term` | `--near-term` |
| 近端日期 | `--near-delivery-date` | `--near-delivery-date` |
| 远端日期 | `--far-delivery-date` | `--far-delivery-date` |
| 期权费 | ❌ 不支持 | `--prem-pips` |
| delta | ❌ 不支持 | `--delta` |

### 典型错误警示

| 用户输入 | ❌ 错误做法 | ✅ 正确做法 |
|----------|-----------|-----------|

## 1. 结构性掉期对客户的补贴价值

结构性掉期的期权费补贴到**掉期的近端**,使得：

- 掉期近端实际成交价比标准掉期更优
- 代价是承担期权被行权的风险

用户除了对 K 和 far-term 参数直接表达，也可以对补贴点数来表达需求

## 2. 用户的表达方式

用户对结构性掉期的表达可以分为专业的直接需求表达和非专业的间接表达。

### 2.1 直接表达

**直接表达**的特点为直接给出符合结构性掉期报价范式的输入模式，也就是 对 K 和 近、远端term 的直接需求。

> **脚本选型**：参见 §0.5 脚本选型决策表。识别完参数后按决策表选择脚本。

### 2.1.0 对近远端日期对的直接要求（**高频场景**）

**输入条件**: 用户给出两个日期（用 `~` / `-` / `到` / `至` / `~` 连接），**无** K / prem / delta

**常见连接符**：

- `2026.06.29~2026.12.31`（波浪号）
- `2026.06.29 到 2026.12.31`（中文"到"）
- `2026-06-29 至 2026-12-31`（中文"至"）
- `2026.06.29-2026.12.31`（短横线）

**识别规则**：

- 前日期（时间较早）→ `near-delivery-date`（近端交割日）
- 后日期（时间较晚）→ `far-delivery-date`（远端交割日）

**映射**：

- 报价范式：**1.2 基准单点报价给双日期求 K（K=FAR）**
- 脚本选型：`opt_structured_swap_query.py`

**示例**：

| 用户输入 | near-delivery-date | far-delivery-date | 脚本 |
|----------|-------------------|-------------------|------|
| "结构性掉期 2026.06.29~2026.12.31 USDCNY" | 2026-06-29 | 2026-12-31 | opt |
| "6月29到12月31 结构性掉期 美元" | 2026-06-29 | 2026-12-31 | opt |
| "USDCNY 结构性掉期 2026-07-01 至 2026-09-30" | 2026-07-01 | 2026-09-30 | opt |
| "2026.06.29~2026.12.31 K=7.10" | 2026-06-29 | 2026-12-31 | **structured**（有 K） |

**调用**：

```bash
python scripts/opt_structured_swap_query.py --user-id {userId} --currency-pair USDCNY --settle-purchase settle --near-delivery-date 2026-06-29 --far-delivery-date 2026-12-31
```

**禁止**：
- ❌ 将此场景调用 `structured_swap_query.py` — 该脚本需要 K/prem/delta 参数，无约束时报错"未知场景"

### 2.1.1 对 far-term 的直接要求

**输入条件**: `far-term` 或 `far-delivery-date` 明确，且 K / target_prem_pips 都未给出

- 例子：`far-term` 明确见示例A1，`far-delivery-date` 明确见示例 A4
- 映射：识别到此目的后，将报价范式映射到 **1.1 基准单点报价给 term 求 K**
  **同时显式给了 far-term 和 far_delivery_date**：
- 同时**显式提供**以 far-term 为准
- 如果同时出现，但其中之一是 **市场观点** 隐含的，以**显式提供**为准
**若给出近端、日期对及term对 时，交割日日期或near-term代表的日期在前的作为 近端 `near-delivery-date` `near-term`**

### 2.1.2 对 K 的直接要求

**输入条件**: `desired_strike` 明确，但 far-term / delivery_date 未给出

- 例子：见示例A2
- 处理：K 不再唯一决定 far-term。结构性掉期需要 far-term 锚定掉期结构，因此须追问 远端far-term。 近端可以默认T+0 
- 映射：通过 `chat` 询问用户希望的期限后，走 **1.4 K 确定求 prem**

### 2.1.3 对 term 和 K 都有要求

**输入条件**: 同时给出了 `desired_strike` 和 `far-term` / `far-delivery-date`

- 例子：见示例E1（已更新为合法输入）
- 处理：K 与 far-term 不再互斥，此为合法输入
- 若仅给 far-term + K → 走 **1.4 K 确定求 prem**
- 若给 far-term + K + prem → 走 **1.5 双目标探索**
- 若给 far-term + K区间 → 走 **1.6 K 区间扫描**

### 2.1.4 Term 对 / 日期对 / term-日期混合对解析规则（近远端识别）

**当用户输入中出现两个 term、两个日期、或 term+日期混合时，均表示近端和远端期限，而非两个独立的远端扫描。**

**识别格式**（常见连接符）：

- `X-Y` / `X~Y` / `X到Y` / `X至Y` / `X与Y` → 解析为近远端期限对

**解析规则**：根据连接符两侧的内容类型，分别匹配到对应参数：

| 左侧内容 | 右侧内容 | 左侧映射 | 右侧映射 | 示例 |
|---------|---------|---------|---------|------|
| term | term | `--near-term` | `--far-term` | `T+3~3M` → near-term=T+3, far-term=3M |
| 日期 | 日期 | `--near-delivery-date` | `--far-delivery-date` | `2026.06.29~2026.12.31` → 双日期 |
| **term** | **日期** | **`--near-term`** | **`--far-delivery-date`** | **`T+3-2026-07-16` → near-term=T+3, far-delivery-date=2026-07-16** |
| **日期** | **term** | **`--near-delivery-date`** | **`--far-term`** | **`2026-06-26~1M` → near-delivery-date=2026-06-26, far-term=1M** |

**term 识别**：以下格式视为 term（非日期）：
- `T+0` / `T+1` / `T+3` / `T+7` / `T+N`
- `ON` / `TN` / `TN+1` / `TN+2`
- `1W` / `2W` / `3W` / `4W`
- `1M` / `2M` / `3M` / `6M` / `1Y`
- `1个月` / `2周` 等中文期限表达

**示例**：

| 用户输入 | near | far | 脚本参数 |
|----------|------|-----|---------|
| `结构性掉期 HKDCNY T+3-2026-07-16` | near-term=T+3 | far-delivery-date=2026-07-16 | `--near-term T+3 --far-delivery-date 2026-07-16` |
| `T+0~2026-12-31 结构性掉期` | near-term=T+0 | far-delivery-date=2026-12-31 | `--near-term T+0 --far-delivery-date 2026-12-31` |
| `2026.06.26~1M USDCNY` | near-delivery-date=2026-06-26 | far-term=1M | `--near-delivery-date 2026-06-26 --far-term 1M` |
| `6M-9M` | near-term=6M | far-term=9M | `--near-term 6M --far-term 9M` |
| `1个月到6个月` | near-term=1M | far-term=6M | `--near-term 1M --far-term 6M` |

**重要：短横线歧义处理**
- `T+3-2026-07-16`：左侧 `T+3` 是 term（含 `T+` 前缀），右侧是日期 → **near-term + far-delivery-date**
- `2026-06-29-2026-12-31`：两侧均为日期格式（含 `20XX` 前缀），`-` 为日期内分隔符 → **双日期 near + far**
- 识别时先判断 `-` 两侧：一侧为 term 格式、另一侧为日期格式 → 混合格式；两侧均为日期 → 双日期

**判定规则**：term/日期代表的时间**在前**的作为近端 `near-term` / `near-delivery-date`，**在后**的作为远端 `far-term` / `far-delivery-date`。

**注意**：不得将 'term对' 误解为"沿曲线扫描多个 term 区间"（范式 1.9）。term 对被用于构造**单次**报价请求，近远端各一个 term。

### 历史格式兼容的标准表达

老系统存在六字段位置格式:

```
产品 币种 期限 中收 方向 产品报价
```

**历史六字段格式** 仅作兼容识别,不作为推荐形态

- 例子：见示例A3
- 映射：识别到此目的后，将报价范式映射到 `1.1 基准单点报价给 term 求 K`

### 2.1.4 方向对比

**输入条件**: 用户同时要求结汇和购汇对比，如 "结汇和购汇都报一下"

- 映射：识别到此目的后，将报价范式映射到 `1.11 方向对比`

### 2.1.5 币种对比

**输入条件**: 用户要求多个币种对比，如 "USDCNY 和 EURCNY 都报一下"

- 映射：识别到此目的后，将报价范式映射到 `1.12 币种对比`

### 2.2 间接表达

**间接表达**的特点是非专业客户的语句中没有直接给出对 K 的要求，而是通过**市场观点**来隐含一个对 K 的位置。

Agent 必须从客户的观点中反推出合理的 K 以及隐含的结汇与购汇方向。由于**市场观点**不是标准的表达，下面会给出几种常见的市场观点表达类型，以及对应的识别方式。

映射：

- 对于隐藏观点为 K 的，确定 K 和方向后，须追问 term，然后走 **1.3 K 确定求 prem**
- 对于**补贴点数表达**和**结果导向表达**，在识别出用户所需要的补贴点数后：
    - 若用户同时给了 term → 走 **1.4 Prem 反求 K**
    - 若用户未给 term → 走 **1.10 按近端补贴点数反查**

#### 2.2.1 否定式观点

**否定式观点** 即用户认为汇率不太可能到达某点位，例如

- "我觉得人民币不会贬值到 7.20"
- "汇率不太可能跌破 6.80"
- "应该不会破 7.30"

**K的推理路径**：用户认为不太可能到达的点位，正是适合作为 K 的位置，因为客户认为不会发生的事件如果确实没有发生，卖出的期权就不会被行权，客户可以获取近端的补贴的期权费，因此客户愿意承担对应的被行权风险。

**方向的推理路径**：客户的方向由表达本身决定：

- "不会贬值到 X" → `direction = settle`(结汇情境)
- "不会升值到 X" → `direction = purchase`(购汇情境)
- "不会跌破""不会破 X" → 需结合上下文判断方向,不确定时通过 `chat` 追问

**映射**：推导出 K 和方向后，追问 term → 走 **1.3 K 确定求 prem**

#### 2.2.2 区间肯定式观点

**区间肯定式观点** 即用户认为汇率大概率会落在某个区间，例如

- "我觉得汇率大概率在 7.00 到 7.10 之间"
- "应该会在 6.95~7.05 这个范围"
- "未来这段时间应该都在 7.0 附近"

**K的推理路径**：用户认为的汇率区间为"高概率发生区"，采用均分区间 K，使得未来汇率的确落在用户所认为的区间时，客户得以获得近端的补贴的期权费，且期权不会被行权。

- 区间明确表述：我觉得汇率大概率在 7.00 到 7.10 之间。K₁ = 7.0 K₂ = 7.10 按照均分区间报价 -> 1.6 K 区间扫描（far-term + [K₁, K₂]）
- 区间模糊表述：“未来这段时间应该都在 7.0 附近”， K₁ = 7.0 - 0.01 K₂ = 7.0 + 0.01 照均分区间报价 -> 1.6 K 区间扫描（far-term + [K₁, K₂]）

**方向的推理路径**：由于区间观点并未对方向做出判断，因此需要结合其他的客户上下文进行方向判断，如果客户没有确定方向，则需要通过 `chat` 追问方向

**映射**：推导出 K 和方向后，追问 far-term → 走 **1.3 K 确定求 prem**

#### 2.2.3 安全边际表达

**安全边际** 表达并非 **市场观点**，而是对 K 给出了 **相对位置** 而非明确的绝对位置。例如：

- "K 离当前现货远一点"
- "我想 K 设保守一点,远离市场价"
- "K 别太冒险"

**K的推理路径**：这类表达没有给出数值和市场观点，无法根据表达得到 K, 因此要通过 `chat` 引导用户给出自己的观点，询问客户是否希望：

- 给出一个具体的 K 值或区间观点
- 如果用户没有给出 K 值或区间观点的意愿，则根据客户的安全边际表达，按照当前市场标准的"保守" / "中性" / "激进"位置自动选取，选取之前要引导客户给出方向的偏好

**方向的推理路径**：这类表达没有给出方向的观点，因此要通过 `chat` 引导客户给出方向性偏好

**映射**：识别到此目的后，追问 far-term → 走 **1.4 K确定 求prem**

#### 2.2.4 补贴点数表达

**补贴点数表达** 为用户没有指定 K 和 far-term，而是对期权费补贴的点数

**K的推理路径**：K 需要按照 `agent_output/quotation_format.md` 的 1.5 按近端补贴点数反查方式得到

**方向的推理路径**：

1. 先确定用户是否有方向性偏好
2. 若无法确定，则使用 `chat` 追问用户的方向偏好
3. 若客户要求每个方向都扫描，则使用 `chat` 与用户协商扫描期限，不超过3个

**映射**：识别到此目的后：

- 若用户同时给了 far-term → 走 **1.4 Prem 反求 K**
- 若用户未给 far-term → 走 **1.10 按近端补贴点数反查**

### 2.3 混合表达

**混合表达** 即客户既给出了直接参数，又给出了市场观点，比如

> "应该在 7.0 附近,不会破 7.15,我做个 3M 结汇的"

**K的推理路径**：这种表达为混合式，规定一个优先级：**直接参数 > 否定式观点 > 区间观点 > 安全边际**

**方向的推理路径**: 如果客户有明确直接参数，以直接参数为准，如果没有，则按照混合式的优先级，参考各个**市场观点**对方向的推理或追问方式。

报价范式映射：

- 直接参数的优先级最高：
    - 如果直接参数为 far-term/far-delivery-date → **1.1 基准单点报价给 term 求 K** 或 **1.1.1**
    - 如果直接参数为 K（无 far-term）→ 追问 far-term 后走 **1.4 K 确定求 prem**
    - 如果直接参数为 K + term → 走 **1.4 K 确定求 prem**
- 如果市场观点隐含 K → 追问 term 后走 **1.4 K 确定求 prem**
- 如果市场观点既隐含 K 又隐含 term → term 明确时走 **1.4 K 确定求 prem**，否则追问

混合表达的详细例子见 example B1

### 2.4 结果导向表达

**结果导向表达** 为用户没有直接提补贴点数，但给出了所希望达成的经过补贴后近端的价格

**K的推理路径**：这种表达必须要结合当前近端交割日对应的即远期的价格，使用即远期价格减和补贴后价格差得到补贴费用，再走补贴点数表达的推理路径

**方向的推理路径**：方向性隐含在了补贴后掉期近端价格与远期价格相对高低中，若补贴后近端价格高于远期价格，则客户是想 sell 掉期，那么方向应该为结汇, 反之购汇

**映射**：推导出补贴点数后：

- 若用户同时给了 term → 走 **1.5 Prem 反求 K**
- 若用户未给 term → 走 **1.10 按近端补贴点数反查**

### 2.5 信息不足情形

仅在以下情况追问:

1. K、far-term、far-delivery-date、target_prem_pips **全部**缺失
2. 方向无法判断
3. 结果导向表达过于模糊,无法映射为 K、term 或 target_prem_pips
4. 组合调用预估超过 6 次预算
   **处理**: 通过 `chat` 追问，不得擅自选择或给定一个传参。

追问模板:

```

```

## 2.7 风格偏好 → `delta_preference`

#### 2.7.1 风格表达映射

| 风格      | 表达关键词              |
|---------|--------------------|
| **激进**  | 激进/多赚/不怕风险/收益优先    |
| **更激进** | 更激进/更激进一点/非常激进/最激进 |
| **保守**  | 保守/稳/风险小/别太冒险      |
| **更保守** | 更保守/更保守一点/非常保守/最保守 |

#### 2.7.2 Delta 数值表（契约层）

风格偏好必须按下列业务约定映射为 Delta 数值:

| 方向 | 风格 | Delta 值           | 符号说明 |
|---|---|-------------------|--|
| **结汇(settle)** | 激进 | **delta = +0.3**  | 正值 |
| **结汇(settle)** | 更激进 | **delta = +0.35** | 正值 |
| **结汇(settle)** | 保守 | **delta = +0.20** |  正值|
| **结汇(settle)** | 更保守 | **delta = +0.15** | 正值 |
| **购汇(purchase)** | 激进 | **delta = -0.30** | 负值 |
| **购汇(purchase)** | 更激进 | **delta = -0.35** | 负值 |
| **购汇(purchase)** | 保守 | **delta = -0.20** | 负值 |
| **购汇(purchase)** | 更保守 | **delta = -0.15** | 负值 |

#### 2.7.3 记忆口诀

> **"结汇正值，购汇负值"**
> - 结汇方向：激进 = 正值(+0.30)，更激进 = 正值(+0.35), 绝对值增大
> - 结汇方向：保守 = 正值(+0.20), 更保守 = 正值(+0.15), 绝对值减小

#### 2.7.4 快速查表

```
用户说"激进" → 先判断方向 → 再确定 delta 符号 -> 再确定delta值
  - 结汇 + 激进 → delta = +0.30
  - 购汇 + 激进 → delta = -0.30

用户说"更激进" → 在激进基础上 +0.05 步长 -> 再确定delta值
  - 结汇 + 更激进 → delta = +0.35（+0.30 + 0.05）
  - 购汇 + 更激进 → delta = -0.35（-0.30 - 0.05）

用户说"保守" → 先判断方向 → 确定 delta 符号 -> 再确定delta值
  - 结汇 + 保守 → delta = +0.20
  - 购汇 + 保守 → delta = -0.20

用户说"更保守" → 在保守基础上 -0.05 步长 
  - 结汇 + 更保守 → delta = +0.15（+0.20 - 0.05）
  - 购汇 + 更保守 → delta = -0.15（-0.20 + 0.05）
```

#### 2.7.5 步长规则

- **激进 → 更激进**：绝对值增加 0.05
- **保守 → 更保守**：绝对值减少 0.05
- 步长固定为 0.05，确保风格梯度平滑过渡

---

#### 2.7.6 递进式调整
当用户在已有报价基础上要求"再 X 一点"时：

```
处理流程：
  1. 记录上一次使用的 delta 值（符号 + 绝对值）
  2. 判断用户意图："更激进" → 绝对值增加 0.05；"更保守" → 绝对值减少 0.05；折中，在用户前一个意图 绝对值反向操作 0.05
  3. 保持符号不变，仅调整绝对值
  4. 使用新 delta 重新报价

示例（购汇 EURCNY 3M）：
  第 1 轮：用户"购汇 报价" → 基准报价（无 delta）
  第 2 轮：用户"激进一点" → delta = -0.30（购汇激进，负值）
  第 3 轮：用户"更激进一点" → delta = -0.35（绝对值 0.3 + 0.05 = 0.35，符号不变）
  第 4 轮：用户"再激进点" → delta = -0.40（绝对值 0.3 + 0.05 = 0.40，符号不变）
  第 5 轮：用户"折中一下" → delta = -0.35（绝对值 0.40 - 0.05 = 0.35，符号不变）
```

#### 2.7.7 边界约束
- delta 绝对值范围为 **0.1 ~ 0.9**
- 当用户要求递进导致绝对值超过 0.9 时，通过 `chat` 提示已达到激进上限
- delta 绝对值低于 0.1 时过于保守，报价意义不大

## 3. 组合模式行为约束

### 3.1 组合模式前提条件

组合模式适用于当用户需求**无法由一次调用完成**，但可以被拆分为若干**语义独立、目标清晰**的子调用时。进入组合模式要求同时满足以下3条：

1. 用户需求确实需要多维度比较或分步完成
2. 每一次调用都能回答"这一次要解决什么子问题"
3. 子调用之间互相独立或有清晰依赖链

### 3.2 先规划后执行

进入组合前必须形成调用计划清单，按计划执行，不在过程中无规划新增调用。

调用计划清单格式：

```
调用 1:<目标> → 参数:<...>
调用 2:<目标> → 参数:<...>
...
汇总方式:<表格 / 筛选后返回>
```

规划与试错的划分：
| 组合求解 | 试错行为 |
|---|---|
| 每次调用的子目标不同 | 目标相同或相似 |
| 产生独立新信息 | 产生冗余信息 |
| 事前有规划 | 事后看结果再决定 |
| 调用数可预期 | 调用数不受控 |

### 3.3 预算交互规则

- 调用次数的预算超出时，通过 `chat` 与用户协商拆分
- 不允许执行中途临时扩展预算
