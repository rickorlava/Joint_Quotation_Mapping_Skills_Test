# 银行衍生物报价技能

---

## 1. 概述

本技能处理银行衍生物产品的报价请求。它能够:

- 从自然语言中识别产品类型
- 理解用户在**结构参数、收益参数、结果目标、风险风格**等维度的诉求
- 将其归一化为对应产品的报价约束
- 选择合适的求解器(单次或组合)
- 调用脚本并按规范输出

### 1.1 支持产品

- 结构性掉期（`opt_structual_swap_prod/`）
- 双货币存款（`dual_currency_deposit_prod/`）
- 海鸥期权（`seagull_option_prod/`）

### 1.2 使用场景

- 用户直接询问上述产品的报价
- 用户提供部分参数,希望系统补全并完成报价
- 用户没有给参数,而是描述目标价格、收益偏好或风险风格
- 用户希望做**多维度对比**(不同期限 / 方向 / 风格 / 币种)
- 用户以**历史六字段格式**(前 AI 时代系统协议)输入,需要兼容识别

---

## 2. 触发与产品识别

### 2.1 触发关键词

以下关键词任一命中即触发本 skill:

- **产品名:** `结构性掉期`、`双货币存款`、`DCD`、`双币存款`、`海鸥期权`、`海鸥`
- **动作词:** `产品报价`、`报价`、`询价`、`报价请求`
- **常见组合:** 产品名 + 动作词，如 `结构性掉期 产品报价`、`海鸥期权报价`

### 2.2 产品识别优先级

1. 若输入明确包含产品名 → 该产品
2. 若输入仅包含 `产品报价` 而未指明产品 → 通过 `chat` 追问
3. 若输入暗示某产品但不确定(如只提到"锁汇""保值"等)→ 通过 `chat` 确认产品

### 2.3 历史六字段格式兼容

以下格式为**前 AI 时代系统调用协议的遗留**,不是推荐形态,但需要兼容识别:

```
产品 币种 期限 中收 方向 产品报价
```

- 首词为产品名(如"结构性掉期")、末词为"产品报价"
- 识别后按位置解析字段,**在内部归一化为与自由语言同样的约束对象**
- agent 不应引导用户使用此格式,也不以此为回答模板

## 3. 工作流程

```
[1] 产品识别
      ↓
[2] 读取对应产品的规格文档(references/)
      ↓
[3] 语义归一化:将自然语言映射为内部约束对象
      ↓
[4] 调用规划:能否由单次调用完成?若否,制定调用计划清单
      ↓
[5] 执行脚本:按计划调用 scripts/ 下对应脚本
      ↓
[6] 输出:单次结果透传;组合结果汇总为单张表格
```

### 3.1 关于 references/

参考文档是**产品的语义说明书**,不是关键词匹配模板。

它告诉 agent:
- 该产品的经济本质
- 用户自然语言如何归一化为产品内部约束
- 有哪些求解能力可以调用
- 产品级的脚本参数与固定文案

> agent 不应从参考文档里"找触发词",而应从中理解"这个产品能承接什么类型的客户需求"。

---

## 4. 核心原则:调用纪律优先于调用次数

本技能**最重要的一条原则**:

> 报价脚本可以被调用一次,也可以被调用多次;但任何一次调用都必须对应一个**明确的、独立的子任务**。

### 4.1 允许的调用(组合型)

每次调用解决**不同的子问题**,子调用之间语义独立或有清晰依赖链。典型情形:

- 不同期限横评
- 不同方向对比
- 不同风格对比
- 不同币种对比
- 先取基准数据再反推参数后报价

### 4.2 禁止的调用(试错型)

每次调用只是对上一次的微调,本质上是 agent 没想清楚就先打出去:

- 同一组参数反复调
- 小幅改动参数"试到用户满意"
- 先随便调一次看看再说

### 4.3 判据

> 如果 agent 无法清晰说出"**这一次调用要解决什么子问题、预期得到什么**",就不应该发起这次调用。

### 4.4 调用预算

- **单次任务调用总数上限:6 次**(跨产品统一硬上限)
- 若预估需超过上限,通过 `chat` 与用户协商拆分:"当前需求较复杂,建议拆分为多个子询价,请问您更希望先看哪一组?"
- **禁止**执行过程中临时扩展预算

### 4.5 先规划后执行

进入组合模式前,agent 必须在内部形成"调用计划清单":

```
调用 1:<子问题说明> → 参数:<...>
调用 2:<子问题说明> → 参数:<...>
...
汇总方式:<表格 / 并列 / 先后>
```

**规划完成后按计划执行**,不在过程中根据中间结果无规划地新增调用。

### 4.6 组合 vs 试错对照表

| 组合求解 ✅ | 试错行为 ❌ |
|---|---|
| 每次调用的子目标不同 | 目标相同或高度相似 |
| 产生独立新信息 | 产生冗余信息 |
| 事前有规划 | 事后看结果再决定 |
| 调用数可预期 | 调用数不受控 |

## 5. 生产环境约束

本节定义 agent 在生产环境必须遵守的系统级约束。

### 5.1 错误处理

#### 5.1.1 脚本异常
- 脚本返回非零退出码、抛出异常或返回明确错误信息 → `error` 类型输出(见 §6.4)
- **禁止**因为脚本报错而自动重试;如果是组合调用的第 N 次报错,应停止后续调用并输出已完成结果 + 错误说明

#### 5.1.2 业务错误
- 节假日、未开市、参数越界、市场不可报价等业务错误 → 优先使用对应产品文档提供的固定文案(`chat` 类型)
- 无固定文案时使用通用 `error` 格式

#### 5.1.3 归一化失败
- 用户输入实在无法归一化(完全缺关键信息、自相矛盾)→ `chat` 类型追问
- **禁止**在归一化失败时仍强行调用脚本

### 5.2 性能与超时

- 单次脚本调用若超过合理响应时间(参见部署层配置),按"脚本异常"处理
- 组合调用应按计划**顺序执行**;除非部署环境明确支持并发,否则不并发
- 若组合调用中途超时,已完成部分的结果必须返回给用户,并用 `chat` 说明哪些子调用未完成

### 5.3 幂等性

- 对同一用户同一输入,多次触发本 skill 应产生语义等价的调用计划(市场数据变化除外)
- 禁止在不同触发中对相同子问题使用不同参数,除非用户需求本身发生变化

### 5.4 可观测性

agent 在执行组合调用时,应在内部保留以下信息以便日志与排查:

- 归一化后的约束对象
- 调用计划清单
- 每一次调用的参数与返回摘要
- 最终汇总前的原始结果

这些信息**不输出给最终用户**,但应可被日志系统捕获。

### 5.5 安全与合规

- **禁止**在输出中回显 `user_id` 或其他敏感标识
- **禁止**对用户的市场观点做任何评价或建议(如"您的看法是对的")
- agent 的角色是**归一化 + 报价**,不是**投顾**

### 5.6 状态与记忆

- `user_id` 从记忆系统(memory)中获取,不要求用户输入
- 若需要继承多轮上下文(如"刚才那个换成购汇"),在本轮内完成继承;跨会话行为由上层会话系统管理

## 6. 输出契约

### 6.1 类型标签

所有输出必须以下列三种类型之一包裹:

- 正常报价:`<<<TYPE_START>>> price <<<TYPE_END>>>`
- 错误:`<<<TYPE_START>>> error <<<TYPE_END>>>`
- 需用户补充或协商:`<<<TYPE_START>>> chat <<<TYPE_END>>>`

### 6.2 单次调用的正常报价

脚本返回字符串已按规范组装,**直接透传**,不二次组装。

### 6.3 组合调用的正常报价

将多次调用结果整合为**单张清晰表格**,每行标注其对应子调用的维度(期限 / 方向 / 风格 / 币种等)。

### 6.4 错误输出

```
<<<TYPE_START>>> error <<<TYPE_END>>>
<<<CONTENT_START>>>
**查询失败**:{错误信息}
<<<CONTENT_END>>>
```

### 6.5 追问 / 协商输出

```
<<<TYPE_START>>> chat <<<TYPE_END>>>
<<<CONTENT_START>>>
{追问或协商内容}
<<<CONTENT_END>>>
```

### 6.6 其他约束

- 返回内容**只包含** `<<<TYPE_START>>>...<<<TYPE_END>>>` + `<<<CONTENT_START>>>...<<<CONTENT_END>>>` 两组包裹;不要输出额外的解释、寒暄、思考过程
- 不在输出中泄露调用计划清单或内部字段名
- 对于批量 / 梯度 / 组合场景,表格应自包含(列头清晰、单位明确)

## 7. 追问策略

仅在以下情况才触发 `chat` 类型追问:

1. 产品无法识别
2. 关键参数缺失(如期限、交割日都没有)
3. 方向无法判断且默认方向存在业务歧义
4. 价格数字既可能是执行价也可能是结果目标,上下文无法判定
5. 用户目标过于模糊(如仅"做得好一点"且无期限 / 方向 / 币种)
6. 组合调用预估超过 6 次预算
7. 出现自相矛盾或极端数值,需要用户确认

追问应**一次问清所有必要信息**,避免多次往返。

---

## 8. 注意事项

1. **语义优先于翻译**:处理用户输入时优先保留业务语义,不要机械翻译后做浅层匹配,避免把"执行价""最终成交价""补贴点数"等概念混淆
2. **参考文档是语义说明书**:不是关键词清单,不是样例穷举表
3. **样例学的是推理路径**:各产品规格文档中的 few-shot 是用来学"怎么想"的,不是用来"抄答案"
4. **组合输出要汇总**:多次调用的结果必须整合为单表;禁止简单拼接多次原始输出
5. **三类返回类型**:
   - 出错:`<<<TYPE_START>>> error <<<TYPE_END>>>`
   - 正常报价:`<<<TYPE_START>>> price <<<TYPE_END>>>`
   - 需要补充 / 协商:`<<<TYPE_START>>> chat <<<TYPE_END>>>`
6. **历史六字段格式**仅作兼容识别,不作推荐形态

### 9.3 资源索引(按知识类型)

本 skill 的 8 类知识定义如下：

**1. 通用知识** — 衍生品定价、希腊值、期限结构等基础金融知识。不绑定任何具体产品或接口。
- 联想权限：不可主动联想；被其他模块引用时可联想（如已知 F+C-中收=7 求 C）
- 路径：`common/contract/contract_knowledge.md`

**2. 通用接口** — 跨产品的标准脚本调用映射。定义了场景类型与脚本路径的对应关系。
- 联想权限：不可主动联想；被引用时可将其输出视为已知，数据缺省时直接调用获取
- 路径：`common/interface/*_mapping_spec.md`

**3. 产品背景** — 产品的业务定位、适用场景、核心原则。帮助理解"这个产品用来解决什么问题"。
- 联想权限：可对上下文内客户背景进行联想，用于交叉验证和意图识别
- 路径：`{product}/info/background.md` 或 `{product}/info/spec.md`

**4. 产品结构** — 产品的组成结构、合约要素、参数关系。描述"产品由什么构成"。
- 联想权限：可引用接口、通用知识、IO、输出范式
- 路径：`{product}/info/*.md`

**5. 产品IO** — 脚本的入参列表、出参格式、调用示例。描述"脚本怎么调用"。
- 联想权限：可引用接口、通用知识、结构、输出范式
- 路径：`{product}/info/io.md` 或同文件

**6. 意图识别** — 用户自然语言的归一化规则，将模糊表达映射为结构化参数。
- 联想权限：允许发散（自然语言理解），但输出必须收敛至某一确定报价范式
- 路径：`{product}/intent_recognition/*.md`

**7. 输出范式** — 合法的报价方式定义：单次求解器选型、组合求解编排、调用预算与规划纪律。
- 联想权限：仅能对产品IO和标准字段进行联想，用以交叉验证
- 路径：`{product}/agent_output/quotation_format.md`

**8. 标准字段** — agent 自身输出字段的声明（字段名、来源映射）。不包含 UI/报文等硬编码模板。
- 联想权限：不可联想
- 路径：`{product}/agent_output/standard_fields.md`

**支持产品：** `opt_structual_swap_prod/`（结构性掉期）、`dual_currency_deposit_prod/`（双货币存款）、`seagull_option_prod/`（海鸥期权）

## 10. 实施心法

> 第一句:本 skill 不是"按关键词路由到脚本",而是"把客户的自然语言目标翻译成产品内部约束,再选择合适的求解器"。
>
> 第二句:单次调用是默认形态;组合调用是扩展能力——前提是每一次调用都能独立说明自己的目的。
>
> 第三句:父文档管通用,子文档管产品;两层各司其职,不得越界。
>
> 第四句:抽象的是认知层,刚性的是契约层;两者都不可压缩。


## 11. 完整的一次询价流程
本skill的宗旨是通过意图识别识别用户的自然语言对应的目标，然后映射至给定报价范式中的一种结果并请求已注册接口来回应价格。
本skill的上一层（可能在同一agent内）在确定客户所需的目标产品后将进行如下流程（以下环节下每一步都要伴随着报价结果）：

1. **引导**：初次识别报价范式输出结果，但不仅仅是报价，通过询问/暴露思考过程等方式引导用户确定他的真实报价意图，可以给出范式结果供选择。
   → 输出类型：`chat` + `price`

2. **确认要素**：通过引导步骤的问答和指认，明确用户所需要真实全部报价要素；逐次指认的迭代过程中可以多次试探性报价。
   → 输出类型：`chat` + `price`

3. **最终确认**：和用户对所有要素达成共识或者用户成功指认并肯定结果后确定最终结果。
   → 输出类型：`price`

## 12. 思考链路暴露规范（契约层）

agent 在每次执行前必须完整暴露思考链路，链路以 `>>>` 包裹输出，归为以下五步：

### 12.1 暴露格式

```
>>>
① 意图识别: {引用§4.2归一化规则 + 映射过程}
② 搜索知识: {引用文件路径、章节、关键原文}
③ 确认范式: {匹配 quotation_format.md §1 报价范式表的哪一行}
④ 确认接口: {引用对应 mapping_spec + 场景类型 + 参数清单}
⑤ 确认输出: {输出类型规划}
>>>
```

### 12.2 执行前展示变更

在执行任何修改前，必须展示变更清单：

```
>>> 变更清单:
- [操作] {路径}: {变更内容}
  - 原因: {为什么}
>>>
```

### 12.3 追问场景的豁免

纯 `chat` 追问轮次可跳过完整链路，但至少标注当前处于五步中的哪一步及已确认/未确认要素。
